# 以 py-xiaozhi 为语音引擎：网页 + 车旁双入口

> 决策：语音能力**统一用 py-xiaozhi**，不再自建 ASR/LLM/TTS 管线，也不引入 bailing。
> 目标：①控制网页里能开语音对话 ②在车旁喊一声就能对话
> 状态：设计稿｜日期：2026-10-22

---

## 0. 结论

py-xiaozhi 已经解决了"车旁唤醒对话"的**全部**问题（唤醒词、VAD、ASR、LLM、TTS、打断、重连）。
缺的只有一件事：**它只会用本地声卡，网页插不进去。**

所以整个方案只有一个核心动作——**把 py-xiaozhi 的音频出入口抽象成"端点"**，让它既能接本地麦克风，也能接网页：

```
              ┌──────────── py-xiaozhi 会话（引擎）────────────┐
              │  唤醒词 / 打断 / ASR / LLM / TTS / MCP 工具     │
              └───────┬───────────────────────────┬───────────┘
                      │                           │
              ┌───────▼────────┐          ┌───────▼────────┐
              │ 端点 A：车旁    │          │ 端点 B：网页    │
              │ 本地麦 + 喇叭   │          │ 浏览器麦克风/喇叭│
              │ （AlsaEndpoint）│          │ （WebEndpoint） │
              └────────────────┘          └────────────────┘
```

## 2. 核心决策：声卡归谁？

这是整个方案唯一真正难的地方，必须现在定。

| 方案 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **① py-xiaozhi 独占声卡** | 网页对话必须绕进 py-xiaozhi；原有网页对讲失效 | 改动最小 | 丢掉"网页听车端/对讲"能力，两套功能二选一 |
| **② IntercomHub 独占，py-xiaozhi 注入后端** ⭐ | 车端 `audio.py` 仍是唯一音频主，py-xiaozhi 用它当声卡 | 网页对讲 + 网页对话 + 车旁对话三件事共存，一套设备 | 要改 py-xiaozhi 音频层（约 150 行）；AEC 退化成半双工 |
| ③ 双声卡物理隔离 | 各用一块 USB 声卡 | 零冲突 | 车上两个麦克风两个喇叭，体验割裂 |

**推荐 ②**。理由：你的目标里"网页能对话"和"车旁能对话"用的是**同一个会话**，如果声卡分家，两边听到/说的内容就不一致了。

**代价说清楚**：`IntercomHub` 是半双工（PTT 独占播放），所以"它说话时你插嘴"会退化成"等它说完"。要真全双工，需要 **硬件 AEC 麦克风**（ReSpeaker XVF3800 之类）——那是硬件层的事，不改这一层设计。

## 3. 架构：把车端 `:8081` 升级成"音频总线"

现在 `:8081` 只服务浏览器。改成三种角色都挂上去：

```
                    ┌──────────────────────────┐
   浏览器(:8081) ───▶│                          │
                    │  audio_ws  （音频总线）   │──▶ 本地声卡（IntercomHub）
   py-xiaozhi ──────▶│  按 dst 路由音频帧        │
     (role=engine)   └──────────────────────────┘
```

### 3.1 新增协议（在现有二进制帧上加一个 JSON 头）

| 方向 | 消息 | 说明 |
|---|---|---|
| engine→总线 | `{"type":"engine","hello":true,"caps":["kws","full_duplex"]}` | py-xiaozhi 注册为引擎 |
| 页面→总线 | `{"type":"dialog","on":true}` | 网页开对话（等价于"喊了一声唤醒词"） |
| 总线→engine | `{"type":"trigger","source":"page"}` | 通知引擎：有人要对话了 |
| engine→总线 | `{"type":"state","state":"listening\|thinking\|speaking"}` | 引擎状态，转发给页面显示 |
| engine→总线 | 二进制（16k PCM） | TTS 音频，总线按 dst 送本地喇叭和/或页面 |
| 页面→总线 | 二进制（16k PCM） | 页面麦克风音频，总线转给 engine |
| 总线→页面 | `{"type":"asr","text":"..."}` / `{"type":"reply","text":"..."}` | 文字回显（做字幕） |

> 好处：**浏览器零改动**（还是那条 WS、同样的 16k PCM 格式），py-xiaozhi 只是多了一个"客户端"身份。

### 3.2 谁来驱动会话

| 场景 | 触发路径 |
|---|---|
| 车旁 | 本地麦克风 → KWS 命中"小智" → py-xiaozhi 内部 `_on_wake_word_detected` → 连接 + 开麦（**现有逻辑，不用改**） |
| 网页 | 页面点「开始对话」→ 总线发 `{"type":"trigger"}` → py-xiaozhi 调 `application.toggle_chat_state()`（现成方法）→ 进入 LISTENING |

两条路径最后都落到同一个会话上，所以**上下文是连续的**：车旁说一半，网页接着问也没问题。

## 5. 分阶段

### 阶段 1：验证车旁唤醒（0.5 天，只差你试一句）
现在就能做：对着 Mac 麦克风说"**小智**"，看状态是否从「未连接」→「聆听中」。
- 若不灵：调 `config.json` 的 `KEYWORDS_THRESHOLD`（0.2 → 0.1 更灵敏）、`KEYWORDS_SCORE`
- 若误触发太多：删掉 `keywords.txt` 里的 `x iǎo zh ì @小智` 这行，只留 4 音节的"小智小智"

### 阶段 2：网页端点（1.5 天）
`:8081` 加 engine 角色 + 页面按「开始对话」。验收：远端点按钮 → 说话 → 车端喇叭出声 + 页面出字。

### 阶段 3：音频合流（2 天）
把 py-xiaozhi 的音频改走 `IntercomHub`（阶段 2 可以先用"py-xiaozhi 独占声卡"的临时方案跑通 UI，再合流）。

### 阶段 4：搬到车上（0.5 天）
- Pi 上按同一份 `models/` 部署（int8 只有 4.8MB）
- py-xiaozhi 必须跑在 `tmux` 里（CLI 模式要真 TTY）
- 树莓派上用 `num_threads=2` 跑 KWS，别和 lerobot 控制环抢核

## 6. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| **2 音节唤醒词误触发** | 环境里"小智"字样多就会乱连 | 只保留"小智小智"；或加 `keywords_threshold` |
| **KWS 常驻占麦** | 与网页对讲抢设备 | 阶段 3 合流后由 hub 统一分配；此前先关网页对讲 |
| **半双工** | 它说话时插嘴听不见 | 硬件 AEC 麦克风（唯一根治） |
| py-xiaozhi 与浏览器抢同一个 account 的 device | 云端可能踢掉另一个会话 | **不要**让浏览器当第二台设备；浏览器只做端点（本方案已规避） |
| Pi 上 CPU 竞争 | 唤醒/ASR 卡顿 | KWS 限 2 线程；ASR 走云端 |
| 断网 | 小智整体失效 | 这是"靠齐 py-xiaozhi"的固有代价，接受或保留降级路径 |
