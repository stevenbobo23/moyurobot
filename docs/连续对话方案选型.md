# 连续对话：能不能做，怎么做到"流畅"

> 回答两个目标：①网页端对话控制小车 ②在车旁直接流畅对话（类"小智"）
> 状态：选型评审稿（未改代码）｜日期：2026-10-22

---

## 0. 先回答：上那份设计能不能开连续对话？

**能开"多轮对话"，但开不了"流畅的连续对话"。** 差两件事，都是底层的：

| 缺口 | 上那份设计的状态 | 后果 |
|---|---|---|
| **全双工**（一边说一边听） | 半双工：SPEAKING 时丢弃上行帧 | 它说话时你插嘴，它听不见；必须等它说完。**这不是"连续"，是"轮流"** |
| **端到端延迟** | 2.7 ~ 4.4 s 到第一声 | 每轮都等 3 秒，聊三轮你就烦了 |

所以上那份设计的价值没变（**先跑通链路、验证声卡和播放**），但它是个"对讲机式问答"，不是"聊天"。

要"流畅"，得换底座。下面是调研结果。

## 1. 开源方案调研

### 1.1 结论速览

| 方案 | 类型 | 能否满足目标 | 判断 |
|---|---|---|---|
| **xiaozhi-esp32-server**（xinnan-tech） | 开源服务端（MIT） | ✅ 能，但协议面向 ESP32 设备 | **最省力的"现成整套"**，但要写浏览器端适配 |
| **py-xiaozhi**（已在 Mac 跑通） | 开源客户端 | ✅ 客户端侧现成 | 和上面配对用 |
| **Qwen-Omni-Realtime**（qwen3.8-omni-flash-realtime） | 官方 API（非开源） | ✅✅ 一条 WS 解决听/想/说/打断 | **推荐主线** |
| **Pipecat / LiveKit Agents** | 开源框架（BSD/Apache） | ⚠️ 能做，但为电话/WebRTC 场景设计 | 对"一台树莓派小车"过重，不推荐 |
| **voice-engine/ec** | 开源（SpeexDSP AEC） | ⚠️ 补 AEC 的软件方案 | 备选，工程量大效果一般 |
| **ReSpeaker XVF3800**（USB 4 麦阵列） | 硬件 | ✅ 直接解决 AEC | **强烈建议买** |

### 1.2 详细点评

**① xiaozhi-esp32-server**（`github.com/xinnan-tech/xiaozhi-esp32-server`）
- MIT，v0.9.7（2026-09-29），150 贡献者、3.7k fork，非常活跃
- 已有：流式 ASR/TTS、VAD、声纹识别、MCP 接入点、视觉、记忆、知识库、Web 控制台
- 关键：它就是 **py-xiaozhi 所连的服务端的开源实现**——把小智官方云换成你自己的一台服务器
- 坑：README 明说"项目未完成、未做安全评估、不建议生产"；协议是给 ESP32 设备的，**浏览器要接进来得自己模拟一个设备端**；依赖 Python 3.10+ 和一堆模型

**② Qwen-Omni-Realtime**（`help.aliyun.com/model-studio/realtime`）
- 官方给的数据：**端到端首音频 1.37 s，每轮约 ¥0.0025**
- 单条 WebSocket 把 ASR + LLM + TTS 收进一个会话：**服务端自己判断轮次**（`semantic_vad`，能过滤"嗯/啊"这类附和声和背景噪音）、**原生支持打断**、**原生 function calling**（模型可以在对话中间调你的工具）
- 输入 16 kHz PCM（正好是车端现有的音频格式），输出 24 kHz
- 接入：`wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime`，吃 `DASHSCOPE_API_KEY`
- 💡 快手验证技巧：老一代模型（`qwen3.5-omni-plus-realtime` / `qwen-omni-turbo-realtime`）**仍可用旧域名** `wss://dashscope.aliyuncs.com/api-ws/v1/realtime`，不用申请 WorkspaceId。先用它把通路跑通，再切到新版专用域名
- 也支持 WebRTC（浏览器直连，自带回声消除），但 **API key 不能放浏览器**，得车端代理

> 这条最关键：**它把"三段式拼接"变成"一条连接"**。上一轮设计里自己写的 VAD / 端点判定 / 打断 / 句子切分 / 串行排队，全部不用写了。

**③ Pipecat（14.4k★，BSD）/ LiveKit Agents（13.1k★，Apache）**
- 2026 年语音 Agent 的两个主流框架，turn detection 和 barge-in 都做得很成熟（Pipecat 的 Smart Turn、LiveKit 的 turn-detector 模型）
- 但它们解决的问题是"**多参与者 + 电话/WebRTC 传输 + 云端伸缩**"，我们的场景是"一台车、一个麦克风、一个喇叭"
- 引入代价：WebRTC 服务器（LiveKit 要自建 media server）、多一层进程、CPU 开销。**对一个跑着 lerobot 控制环的树莓派，不值得**

**④ AEC —— 这是"车旁流畅对话"的真正门槛**
- **ReSpeaker XVF3800**（USB 4 麦阵列，XMOS 芯片做硬件 AEC）：官方说法是 80 dB 播放大音量下仍能瞬时捕获插话；对上层就是个普通 USB 声卡，`arecord` 直接拿到已消回声的音轨。**几乎零软件改造**
- **voice-engine/ec**：Linux 上用 SpeexDSP 做 AEC，靠命名管道/ALSA 插件把播放数据当参考信号。要改现有 `aplay` 架构，工程 2~3 天，效果不如硬件
- **取巧**：TTS 播放时抬高 VAD 阈值、丢掉前 300 ms。只能做到"伪全双工"，插话会丢字

> ⚠️ **网页端不需要 AEC**——浏览器的 `getUserMedia({echoCancellation:true})` 自带。AEC 只是"车旁说话"的问题。

## 2. 三个可行架构

### 方案 A：小智自建服务端（最省力的"整套现成"）

```
py-xiaozhi（车上，已跑通） ──WS──┐
                                 ├── xiaozhi-esp32-server（自建，一台小主机/云）
浏览器（模拟设备协议）──WS───────┘         │
                                    ASR/LLM/TTS/VAD/MCP
                                           │
                                    调车端 /control
```
- ✅ 不用自己写对话逻辑，连续对话/打断/VAD 都由服务端管
- ✅ 记忆、声纹、知识库白送
- ❌ 浏览器要模拟 ESP32 设备协议（hello/listen/audio/abort），约 300 行 JS，且协议会随上游变
- ❌ 服务端要单独一台机器（树莓派跑 lerobot 再跑这个会炸）
- ❌ AEC 问题它也不解决（那是硬件层）

### 方案 B：Omni Realtime 端到端（⭐ 推荐主线）

```
┌─ 车端（Pi）── 一个 WS 客户端 ────────────────┐
│   麦克风(AEC后) ──16k PCM──→ qwen3.8-omni-realtime
│   ←──24k PCM── 喇叭                          │
│        ↑                                     │
│        └─ function calling → 车端工具         │
│           (move_robot / look_and_analyze ...)│
└──────────────────────────────────────────────┘
        ↑ 也可以从网页端点喂音频/出音频
```
- ✅ 延迟 ~1.4 s，原生 semantic VAD + 打断，不用自己写轮次判定
- ✅ 原生 function calling 控车，和上一轮的 8 个工具白名单完全兼容
- ✅ 一条连接，代码量比三段式少一半（扔掉 ASR/句子切分/TTS 播放队列）
- ⚠️ 强依赖 DashScope（断网即哑），且要用 WorkspaceId 专用域名
- ⚠️ 输出 24k，和现有 16k 喇叭要重采样（`soxr` 一行）

### 方案 C：三段式自建（上一轮的方案）

保留作为 **fallback**：Omni 不可用、或营地断网要有基本能力时用。接受 3~4 s 延迟 + 半双工。

## 3. 推荐架构：一个"音频端点"抽象

这是同时满足目标 1 和 2 的关键设计。**对话引擎不关心人在哪，只关心音频从哪来、到哪去。**

```
        ┌──────────── 对话引擎（Omni Realtime 会话）────────────┐
        │  输入: PCM16k   输出: PCM24k   工具: 车端 8 个          │
        └───────┬───────────────────────────────┬───────────────┘
                │                               │
        ┌───────▼────────┐              ┌───────▼────────┐
        │ 端点：车端本地  │              │ 端点：网页      │
        │ ALSA 麦 / 喇叭  │              │ WS :8081        │
        │ (需硬件 AEC)    │              │ (浏览器自带AEC) │
        └────────────────┘              └────────────────┘
```

**端点抽象要提供四个动作**：`read_pcm()` / `write_pcm()` / `on_barge_in()` / `close()`。

- 目标 2（车旁对话）→ 挂本地端点
- 目标 1（网页对话）→ 挂网页端点
- **两个同时挂** → 人在车旁说话，远端网页也能听到对话（"看护模式"），这就是营地里最有用的形态

而且这层能复用现有 `IntercomHub`：
- 本地端点 ≈ `hub` 的一个 listener（收）+ `begin_talk`（发）
- 网页端点 ≈ 现有 `audio_ws` 的二进制帧通道（已经是 16k PCM 双向）

> 所以网页端**不需要改协议**，只要新增 `{"type":"dialog","on":true}`，剩下的复用上一轮设计里那份消息表。

## 4. 和上一份设计的差异

| 上一轮的设计 | 现在改成 | 原因 |
|---|---|---|
| 三段式 ASR→LLM→TTS | **一条 Omni Realtime WS** | 延迟 1.4s vs 3~4s；轮次判定/打断免费 |
| 自己写 VAD 端点检测 | 交给 `semantic_vad` | 它连"嗯/啊"都能过滤，自己写比不过 |
| 自己写句子切分 + TTS 队列 | 不需要 | 模型直接吐音频流 |
| 半双工硬隔离 | **全双工**（靠 AEC） | 否则永远做不到"打断" |
| `hub.begin_talk` 独占播放 | 改为"对话引擎 = 常驻本地说话人" | 全双工时播放不能锁死麦克风 |
| 工具白名单 8 个 | **不变** | function calling 的 schema 一样 |
| 消息协议 | **不变** | `dialog` 那套继续用，只是后端换了 |

**保留不变的部分（依然是对的）**：`can_talk` 鉴权、异常先 `stop_robot()`、动作回显到页面、`duration ≤ 3s`、音量 `dialog_gain`。

## 5. 落地路径（含"先验证再动手"）

### 阶段 0：验证 Omni Realtime 可用性（0.5 天，最关键）

不写业务代码，只验证四件事：
1. 你的百炼账号能用 `qwen3.8-omni-flash-realtime`（要拿 WorkspaceId）
2. 车端（或 Mac）能连上 `wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/realtime`
3. 16k PCM 推上去、24k 音频下来，**实测首音频延迟**
4. function calling 能调到 `http://127.0.0.1:8080/control`

> 第 4 条最关键：模型得能在"说话过程中"调工具。验证过不了，直接转方案 A 或 C。

### 阶段 1：车旁连续对话（2 天）
- 装 ReSpeaker XVF3800（或用现有麦先跑"轮次式"，AEC 到位后再开全双工）
- 车端 `core/dialog/realtime.py`（约 250 行）：WS 会话 + 端点抽象 + 工具桥
- 验收：连续 5 轮不中断；说话打断它；说"往前走一点"车动

### 阶段 2：网页端点（1.5 天）
- 页面加 `dialog` 消息 + 对话面板（上一轮设计的 UI 不变）
- 音频走现有 `:8081` 二进制帧
- 验收：远端网页对话同样流畅；本地喇叭同时出声

### 阶段 3：双端点共存（1 天）
- "看护模式"：车旁说话 + 网页只读旁听
- 权属仲裁：现场说话优先（`can_talk` 让位）

### 备选路径（Omni 不可用时）
方案 A（小智自建服务端）→ 需要一台额外机器；或方案 C（三段式）→ 接受 3~4 s 延迟。

## 6. 成本量级

| 项 | 量级 | 依据 |
|---|---|---|
| Omni Realtime | 每轮 ~¥0.0025 | 官方文章中给的数字 |
| 一次 10 轮对话 | 约 ¥0.025（两三分钱） | 同上 |
| 每天 50 轮 | 约 ¥0.13/天 | — |
| ReSpeaker XVF3800 | 一次性硬件投入 | 见官方渠道 |

> 结论：**对话成本可以忽略**，真正的成本是硬件 AEC 和你的开发时间。

## 7. 待你确认

1. **百炼账号有 `qwen3.8-omni-flash-realtime` 权限吗？**（决定主线走 B 还是 A/C）
2. **能不能买一块硬件 AEC 麦克风阵列？**（ReSpeaker XVF3800 或同类 USB 会议麦）——这直接决定"流畅"能不能成立
3. **营地会不会断网？** 断网就要留方案 C 的降级路径
4. **网页端和车旁对话，哪个先要？** 车旁（目标 2）价值更高但依赖硬件；网页（目标 1）可以先用浏览器自带 AEC 立刻做
