## 2. 它凭什么听起来"流畅"（这是重点）

小智服务端**是三段式管线，不是端到端模型**。它的流畅靠三件事：

```python
# core/connection.py:803-850（简化）
for response in llm_responses:                  # ① LLM 流式
    if self.client_abort: break                 # ③ 随时可打断
    self.tts.tts_text_queue.put(                # ② 每个增量立刻塞给 TTS
        TTSMessageDTO(sentence_type=MIDDLE, content_detail=content)
    )
```

1. **LLM 流式 → 逐块塞 TTS 队列**：不等整段生成完，第一句就先合成
2. **TTS 流式**（EdgeTTS `communicate.stream()`）→ 音频队列 → 边合成边发
3. **`client_abort` 打断**：一旦标记，LLM 生成中断 + `clear_queues()` 清空 TTS/音频队列（`connection.py:1097`）
4. **VAD 端点只有 200 ms**（双阈值 0.5/0.3 + 3 帧窗口）——不是"等 800ms 静音"

> ⚠️ **这修正了我上一轮的判断**：我说"三段式做不到流畅"太绝对了。小智就是三段式，它靠 **200ms 端点 + 全链路流式 + 打断** 达到可接受体验。omni-realtime 的优势是"省代码 + 更低延迟"，不是唯一路径。

## 3. 我们该抄什么（对着车端实际情况）

| 环节 | 我上一轮的选型 | 小智的做法 | 建议 |
|---|---|---|---|
| **VAD** | 能量阈值 + 静音 800ms | **Silero VAD，200ms，双阈值** | ✅ **直接抄**。模型 2MB，Pi 跑得动，效果降维打击 |
| **TTS** | DashScope `cosyvoice-v1`（按字付费） | **EdgeTTS / XiaoxiaoNeural（免费）**，进阶火山"湾湾小何" | ✅ **换成 EdgeTTS 起步**，零成本、真流式；要更好听再上火山大模型音色 |
| **ASR** | `qwen3-asr-flash`（云，按量） | **SenseVoiceSmall 本地** | ⚖️ 二选一：怕吃 CPU 就用云（小智也支持这个选项）；要断网就用本地 |
| **LLM** | `deepseek-flash` | **glm-4-flash**（默认）/ 也可 DeepSeek | ✅ 保持 DeepSeek，和小智的备选项一致，function calling 更稳 |
| **打断** | 自己设计 | `client_abort` + `clear_queues()` | ✅ 语义直接照搬 |
| **管线** | ASR→LLM→TTS 串行 | 流式穿透（三级队列） | ✅ 抄队列模型 |

### 三个最划算的动作

1. **TTS 换 EdgeTTS** —— 立刻把每轮成本从"几分钱"降到 **0**，且音质更自然（"小智味"主要来自这里）
2. **VAD 换 Silero + 200ms** —— 这是"连续对话不卡顿"的关键参数，比换模型影响大
3. **抄三级队列 + abort** —— 让第一句话在 1 秒内出来，而不是等整段合成

## 5. 修正后的两条路线

**路线甲：照抄小智（推荐先做，成本近 0）**
```
Silero VAD(200ms) → SenseVoiceSmall 或 qwen3-asr-flash
                  → DeepSeek(流式, function calling)
                  → EdgeTTS(流式) 或 火山"湾湾小何"
                  → 三级队列 + client_abort 打断
```
- 优点：**零 TTS 成本**、断网可用（本地 ASR/TTS 可换）、有现成代码可抄、音色就是"小智那个味"
- 缺点：要自己拼三级队列（约 300 行）；延迟约 1.5~2.5 s

**路线乙：omni-realtime（省代码）**
```
一条 WS：16k PCM 进 → semantic_vad + 打断 + function calling → 24k PCM 出
```
- 优点：不用写 VAD/队列/打断，约 250 行搞定；延迟 ~1.4 s
- 缺点：按轮付费（约 ¥0.0025/轮，其实也很便宜）、强依赖云端

> 两者不冲突：**VAD + 打断的交互设计可以共用**，先做甲（能立刻听到声音、成本为零），觉得延迟不满意再切乙。

## 5.5 算力：需要 GPU 吗？

**不需要。** 四个环节里三个根本不在本地算：

| 环节 | 在哪算 | 本地算力 | GPU |
|---|---|---|---|
| Silero VAD | 本地 CPU（ONNX，**1.2~2.2 MB**） | 可忽略（<1% 单核） | ❌ 不需要 |
| SenseVoiceSmall | 本地 CPU（ONNX/CPU 推理，`num_threads=2`） | 权重约 200~250 MB，Pi 4 上约 0.3~1 倍实时 | ❌ 不需要 |
| LLM（DeepSeek / glm-4-flash） | **云端** | 0 | ❌ 不需要 |
| TTS（EdgeTTS） | **微软云端** | 0（只吃网络） | ❌ 不需要 |

真正需要 GPU 的只有两件事，**都不在我们的路线上**：

- 本地跑大模型（`OllamaLLM → qwen2.5`、`XinferenceLLM → qwen2.5:72b`）
- 声音克隆（`GPT-SoVITS` / `FishSpeech`）

### ⚠️ 真正的坑不是 GPU，是 torch

- 小智服务端的 **Silero VAD 用 `torch.hub.load()`**（`vad/silero.py:15`）——推理在 CPU，但**要装 PyTorch**
- **FunASR 版 SenseVoice 也走 torch**（`asr/fun_local.py:56` `AutoModel(...)`，`device="cuda:0"` 是注释掉的，说明默认就是 CPU）
- 树莓派（ARM Linux）装 torch 很痛：官方没有现成 aarch64 wheel，往往要编译或依赖第三方源

**规避办法：用 `sherpa-onnx` 一条依赖同时覆盖 VAD + ASR**，全 ONNX、纯 CPU、无 torch。
已确认我们环境里就有（py-xiaozhi 的 venv 装的是 **1.13.8**）：

```python
import sherpa_onnx as so
hasattr(so, 'VoiceActivityDetector')   # True
hasattr(so, 'VadModelConfig')          # True
hasattr(so, 'SileroVadModelConfig')    # True
```
- VAD → `sherpa_onnx.VoiceActivityDetector`（内置 Silero）
- ASR → `sherpa_onnx.OfflineRecognizer` 加载 SenseVoice ONNX 模型
- 一个 wheel、无 torch、ARM 上有现成 aarch64 包

### 真机上的真实约束（CPU 和内存，不是显卡）

| 设备 | VAD + SenseVoice 可行性 | 注意 |
|---|---|---|
| Mac（开发机） | 轻松 | 先在这上面调通 |
| Pi 5（4 核 A76） | 舒适 | 可以和 lerobot 控制环共存 |
| Pi 4（4 核 A72） | 能跑，需实测 | **限 2 线程 + `nice`**，别和控制环抢核；内存 2GB 版本要算账 |
| Pi 3 / Zero | 困难 | 建议 ASR 上云（`qwen3-asr-flash`） |

> 结论：**先别买显卡，也别急着装 torch。** 真机唯一要做的验证是"ASR 一句话要多久"——如果超过 1.5 s，把 ASR 换成云端就行，VAD 仍留本地（它几乎不花钱）。

## 6. 一句话结论

> 小智不是"用了什么神模型"，而是**用对了三个便宜零件 + 三级流式队列**：
> `Silero VAD（200ms 端点）` + `glm-4-flash / DeepSeek` + `EdgeTTS / 火山音色`。
> 我们原方案里最该换的就是 **TTS（省 100% 成本）和 VAD（决定流畅度）**，而 LLM 其实已经和小智同级。
