# 给摸鱼车装上「小智」——语音对话接入方案

> 状态：**方案评审稿，未改任何代码**
> 涉及两个仓库：`~/workspaces/moyurobot`（车端，LeKiwi + Flask + MCP）与 `~/workspaces/py-xiaozhi`（小智 Python 客户端）
> 日期：2026-10-22

---

## 0. 结论先行

用小智现成的 `py-xiaozhi` 客户端去做语音，比自己写一套 ASR/LLM/TTS 划算得多——它已经把「唤醒词 → VAD → Opus 上传 → 云端 LLM → TTS 回落 → 播放」整条链路跑通了，还自带设备激活、断线重连、AEC。

但它和摸鱼车有**一个硬冲突**：**麦克风和喇叭都是独占资源**，两边都要抢。

所以路线的分水岭不在「怎么接语音」，而在「**声卡归谁**」：

| 路线 | 声卡归属 | 改动量 | 出效果 | 评价 |
|---|---|---|---|---|
| **A. 双声卡旁挂**（推荐先做） | 各用一块 USB 声卡，物理隔离 | 只新增 1 个文件 | ~1 天 | 最快、最稳、零回归 |
| **B. 音频合流** | 全部归 `IntercomHub`，小智借道 | 两边各 300~500 行 | ~3 天 | 体验最好（一个麦克风一个喇叭） |
| **C. 协议内嵌** | 全部归 `IntercomHub` | 车端 800+ 行 | ~4 天 | 最干净但等于自己维护一套小智协议 |

**建议：A 先跑通体验 → 满意后再演进到 B**。C 不推荐，除非后面要做高度定制（比如把 TTS 直接喂给车的动作编排）。

## 1. 现状盘点（决定方案的关键事实）

### 1.1 车端 `moyurobot/pi_client`

| 事实 | 位置 | 对方案的影响 |
|---|---|---|
| 有全局音频中枢 `IntercomHub`：**单路采集 + 多路下发 + PTT 独占播放** | `moyurobot/core/audio.py:544` | 它已经是声卡的实际持有者，小智要进来必须和它谈 |
| 采集是**惰性**的：只有存在监听者时才 `arecord` | `audio.py:793` 的 `_capture_loop` | 平时麦克风是空闲的，所以「不冲突」只在没人开网页监听时成立 |
| 播放走 `begin_talk()` 独占 | `audio.py:622` | 已有「非浏览器客户端借喇叭」的先例——打招呼就是 |
| **打招呼（TTS 播报）就是用 `hub.begin_talk(SPEAKER_ID)` 借喇叭的** | `greeting/speech.py:345` | ⭐ 这是 B 路线可行的最有力证据，不用从零设计 |
| 有 `respect_intercom` 策略：对讲中不插话 | `config/default.json:79` | 说明「谁在说话」的仲裁机制已有雏形，可直接扩展给小智 |
| 语音格式：16 kHz / 单声道 / 100 ms 一包 / S16_LE | `audio.py:55` | 小智是 48 kHz + Opus 60 ms 帧，中间需要重采样+编解码适配 |
| 动作能力已封装成 **21 个 MCP 工具**（`move_robot` / `rotate_robot` / `play_preset_action` / `capture_and_analyze` …） | `moyurobot/mcp/server.py` | 语音控制的"手"已经现成，不用重写 |
| HTTP 控制接口 `/control` 存在，但需要先 `/startmove` 打开 `_movement_enabled` | `web/controller.py:236,263` | 语音调动作时得先确保运动使能，否则静默失败 |
| MCP HTTP 与 Web 同进程（:8000 + :8080），共享同一个机器人连接 | `scripts/start_all.sh` | 不要再起第二个进程去连机器人，会抢串口/摄像头 |
| **已经有一条通往小智云的通路**：`pipe.py` + `MCP_ENDPOINT=wss://api.xiaozhi.me/mcp/?token=...` | `mcp/pipe.py`、`start_all.sh` | ⚠️ 云侧 agent 可能已经能调车端工具了，别重复注册 |

### 1.2 小智端 `py-xiaozhi`

| 事实 | 位置 | 对方案的影响 |
|---|---|---|
| CLI 模式可无 GUI（`--mode cli`），但有 GUI 才有表情/托盘 | `main.py` | 车端 headless 就用 CLI |

| MCP 是**设备端注册工具**模式：本地工具 → `type:mcp` 消息 → 云 LLM 反向 `tools/call` | `src/mcp/mcp_server.py:205` + `protocols/protocol.py:202` | ⭐ 加一个 `src/mcp/tools/robot/` 就能让语音驱动车，**不用碰协议层** |

## 2. 冲突清单（照这个逐条排掉）

| # | 冲突 | 严重度 | A 路线处理 | B 路线处理 |
|---|---|---|---|---|
| 1 | **麦克风独占**（arecord vs PortAudio） | 🔴 致命 | 各用一块声卡 | 车端 hub 唯一持有，小智改走注入 |
| 2 | **喇叭独占**（aplay vs PortAudio） | 🔴 致命 | 同上 | 小智 TTS 走 `hub.begin_talk` |
| 3 | 全双工 vs 半双工语义 | 🟠 高 | 隔离后无冲突 | 退化为半双工（播报时不采音），与 hub 现有语义一致 |
| 4 | AEC 回声消除拿不到参考信号 | 🟠 高 | 各自独立，小智自己 AEC | 拿不到参考信号 → 必须半双工，否则自问自答 |
| 5 | **摄像头 `/dev/video0` 抢占** | 🟠 高 | 配置里关掉小智 `take_photo`，识图改走车端 `capture_and_analyze` | 同 A |
| 6 | 云侧工具重复注册（pipe 的 MCP 接入点 + 本地工具） | 🟡 中 | **二选一**，建议保留本地工具、停 pipe | 同 A |
| 7 | Pi 算力：KWS + AEC + Opus + lerobot 控制环并存 | 🟡 中 | 实测 CPU；Pi 4 建议降 `detect_fps`、关 AEC | 同 A |
| 8 | 声学串音：小智喇叭说话被对讲麦克风收进去 | 🟡 中 | 播报时暂停网页监听下发 | hub 内部统一计时，天然可解 |
| 9 | CLI 无 TTY | 🟡 中 | tmux 里跑 | 同 A |
| 10 | 激活/账号绑定 | 🟢 低 | 一次性 | 同 A |

## 3. 三条路线展开

### 方案 A：双声卡旁挂（推荐先做，~1 天）

```
┌────────────────────── Raspberry Pi ──────────────────────┐
│                                                          │
│  moyurobot (Flask :8080 + MCP :8000)                     │
│    └─ IntercomHub ── alsa ── [声卡1: USB麦 + 车喇叭]      │  ← 网页对讲 / 自动打招呼
│                                                          │
│  py-xiaozhi (CLI in tmux)                                │
│    ├─ AudioCodec ── PortAudio ── [声卡2: USB麦+小音箱]    │  ← 语音对话
│    └─ McpServer ── robot 工具 ── HTTP ── :8080/control    │  ← 语音 → 动作
│                                                          │
└──────────────────────────────────────────────────────────┘
```

**改动**
- 小智侧：**新增** `src/mcp/tools/robot/`（约 120~150 行，不修改任何既有文件），提供 `move_robot` / `rotate_robot` / `stop_robot` / `play_action` / `look_and_analyze` / `get_robot_status`，内部用 `requests` 打 `127.0.0.1:8080`，并在首次调用时自动 `POST /startmove`。
- 车端：**零改动**。只在 `.env` 里把小智的 `AUDIO_CAPTURE_DEVICE` / `AUDIO_PLAYBACK_DEVICE` 指到不同声卡（或干脆不配，靠 PortAudio 自动挑第二块）。
- 云侧：小智 agent 里确认**没有**把车端的 MCP 接入点一起绑上（避免两套 `move_robot` 让 LLM 乱选）；绑了就解绑或停 `pipe`。

**优点**：零回归、可回滚（`Ctrl+C` 掉 tmux 而已）、两边各自升级互不影响、AEC 正常。
**缺点**：两个麦克风两个喇叭，成本多一块 USB 声卡（约 30~60 元）、车体走线多一根、两个系统都会"听到"彼此说话。

**快速验证命令**（在 Pi 上，先不改代码也能验到 80%）
```bash
# 1. 看声卡
arecord -l && aplay -l

# 2. 小智独立跑通（先确保它只说不动）
cd ~/workspaces/py-xiaozhi
python main.py --mode cli          # 在 tmux 里；首次会要求激活码

# 3. 车端同时跑网页对讲，确认两边不打架
cd ~/workspaces/moyurobot/pi_client && ./scripts/start_all.sh
```

### 方案 B：音频合流（体验目标态，~3 天）

一个麦克风一个喇叭，`IntercomHub` 是唯一持有者，小智变成 hub 的"本地客户端"。

```
        ┌── 网页监听（ws :8081）──┐
麦克风 ─┤                          ├─→ IntercomHub ─→ 喇叭
        └── 小智 AudioCodec ───────┘        ↑
                 (注入式后端)        打招呼 TTS 也走这里
```

**关键设计（都是已有机制的延伸，不是新发明）**

1. **给 hub 加"本地消费者"概念**
   `_capture_loop` 里现在判断 `has_listener or ptt`（`audio.py:801`）。加一个 `self._local_consumers`，条件变成 `has_listener or has_local or ptt`。小智在 LISTENING 态注册自己 → 麦克风常开；IDLE 态注销 → 回到惰性省电。

2. **播放复用 PTT 通道**
   照 `greeting/speech.py:345` 的写法：`begin_talk("xiaozhi-tts")` → `write_talk()` → `end_talk()`。刚好 `end_talk` 会 drain 播完再关，节奏天然对。

3. **小智侧做一个"Hub 音频后端"**
   在 `py-xiaozhi` 加 `src/audio_codecs/hub_backend.py`，实现和 `sd.InputStream/OutputStream` 同接口的最小对象（`read/write/close`），由环境变量 `XIAOZHI_AUDIO_BACKEND=hub` 选择；48k↔16k 用现成的 `soxr`。
   `XIAOZHI_DISABLE_AUDIO=1`（`application.py:319`）可作为不做任何改造时的降级开关。

4. **仲裁策略（必须定死，否则会自问自答）**
   - 小智播报期间：hub 暂停向网页下发 + 暂停打招呼（复用 `respect_intercom` 的思路，加 `respect_xiaozhi`）
   - 网页对讲期间：小智进 SPEAKING 但不收音（半双工），或直接 abort
   - 打招呼 vs 小智：打招呼优先让路（它是氛围，不是功能）

**风险**：AEC 没有参考信号 → 只能半双工，做不到像真小智音箱那样"说话时也能被打断"。如果这个体验必须要，就得让 hub 把播放数据同时喂给 AEC（`aec_processor.py` 有接口，但要多写一段）。**建议先接受半双工**。

---

### 方案 C：协议内嵌（不推荐，仅列出）

在 `moyurobot` 里实现小智 WebSocket 协议（hello / listen / tts / mcp），音频直接走 hub，不装 `py-xiaozhi`。

- 优点：架构最干净、单进程、无进程间通信、CPU 最省
- 缺点：等于自己维护一份协议实现（`protocols/websocket_protocol.py` 558 行 + `application.py` 1541 行的状态机，能砍到 600~800 行但会持续跟丢上游更新）
- 适用：以后要做"语音直接编排机械臂动作"这类深度定制时才值得

## 4. 推荐执行路径（阶段化，每阶段可独立回滚）

### 阶段 0 — 环境探针（0.5 天，不改代码）

目标：**先确认 Pi 能不能装得动小智**，这是最大的未知数。

```bash
python -V                                    # 需 3.9~3.12
python -m venv ~/venv-xiaozhi && source ~/venv-xiaozhi/bin/activate
pip install sounddevice sherpa-onnx opuslib websockets==11.0.3 aiohttp psutil \
            numpy==1.26.4 soxr pillow colorlog requests pypinyin py-machineid \
            cryptography websockets paho-mqtt opencv-python-headless
# 单独试两个最容易挂的
pip install webrtcvad-wheels==2.0.14         # aarch64 可能没 wheel
python -c "import sherpa_onnx, sounddevice; print('ok')"
sudo apt install -y libportaudio2 alsa-utils
```
判定：`sherpa_onnx` + `sounddevice` 都能导入 → 继续；失败了先解决 wheel，别急着改代码。

### 阶段 1 — 小智独立说话（0.5 天）

1. `python main.py --mode cli`（tmux 里），走 v2 激活，`xiaozhi.me` 绑设备
2. 下 sherpa-onnx KWS 模型到 `models/`（`encoder.onnx` / `decoder.onnx` / `joiner.onnx` / `tokens.txt`），把 `keywords.txt` 写成拼音格式，例如
   `x iǎo zh ì` 这类（当前文件是个无效占位）
3. 用键盘 TTY 先测一轮完整对话（链路通了再谈唤醒词）
4. 验收：**对着麦克风说一句 → 小音箱出声回答**，且车端网页对讲仍然正常

### 阶段 2 — 语音驱动车（0.5 天）

- 新增 `py-xiaozhi/src/mcp/tools/robot/`，注册 6 个工具，全部打到 `127.0.0.1:8080`
- 动作安全性：默认限速 `slow`、`duration ≤ 3s`、进入前自动 `/startmove`、连续 30 秒无指令自动 `/stopmove`
- 云侧清理：解绑/停掉 `pipe.py` 那条 MCP 接入点，避免工具重名
- 验收：说"往前走一点"→ 车动；说"看看前面有什么"→ 走车端 `capture_and_analyze`（复用 DeepSeek 视觉，别用小智自己的摄像头工具）

### 阶段 3 — 合流到单麦克风单喇叭（2~3 天，可选）

按方案 B 做，做完删掉第二块声卡。

### 阶段 4 — 策略打磨（1 天）

打断优先级、播报时静音网页、招呼与小智互斥、日志里能看出"这句是谁说的"。

1. **Pi 型号与 Python 版本？**（Pi 4 / Pi 5，`python3 -V`）—— 决定 KWS+AEC 是否吃得消
