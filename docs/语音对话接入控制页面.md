# 控制页面「语音对话」设计

> 目标：在小车控制页面里直接跟它说话，**车端喇叭出声回复**，页面同步显示对话文字。
> 状态：设计稿（未改代码）｜涉及仓库：`~/workspaces/moyurobot/pi_client`
> 日期：2026-10-22

---

## 0. 一句话结论

**页面已有的两条管道正好够用，不要重造。**

- 上行：浏览器已经把麦克风采成 **16 kHz / 单声道 / 100 ms 一包的 PCM**，通过 WS `:8081` 二进制帧发到车端（`audio_control.js` 的 worklet + 重采样）。
- 下行：车端 `IntercomHub.begin_talk()/write_talk()` 已经能把任意 PCM 播到车上喇叭（自动打招呼就是这么放 TTS 的，`greeting/speech.py:345`）。

所以缺的只有中间一段：**端点检测 → ASR → LLM → TTS**。全部是新增模块，不动现有链路。

```
浏览器麦克风 ──(已有 WS 二进制帧)──┐
                                  ├─→ 【新增】对话管线 ─→ IntercomHub ─→ 车端喇叭
车端 ASR ← PCM ← 端点检测 ─────────┘         │
                                          LLM(DeepSeek+工具)
                                             │
页面文字/状态 ←──(已有 WS JSON 通道)──────────┘
```

## 1. 为什么不是"把 py-xiaozhi 接进来"

| 对比项 | 复用 py-xiaozhi | 在控制页面内建管线（本方案） |
|---|---|---|
| 声卡 | 要跨进程桥接，抢独占 | **零冲突**，复用 `IntercomHub` |
| 一个麦克风 | ❌ 需要双声卡或改造 | ✅ 天然单路 |
| 页面体验 | 要在两个窗口间切换 | ✅ 说话和看画面在同一个页面 |
| 可定制 | 受上游协议约束 | ✅ 想加"看一眼前面"就加个工具 |
| 工作量 | 桥接改造 ~3 天 | MVP ~1.5 天 |

py-xiaozhi 仍然有它的价值（真实小智账号的闲聊能力、唤醒词），但**"控制页面里对话"这件事它做不到**，因为它只管自己的窗口。

## 3. 技术选型

### 3.1 ASR：DashScope `qwen3-asr-flash`（HTTP）

- 端点：`POST https://dashscope.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation`
- 入参：`messages[0].content = [{"audio": "data:audio/wav;base64,..."}]`，`parameters.asr_options.enable_itn`
- 鉴权：`DASHSCOPE_API_KEY`——**和现有 TTS 是同一把钥匙**，车端 `.env` 里已经有（`dashscope_tts.py:41` 兼容 `QWEN_API_KEY`）
- 支持 SSE 流式（`X-DashScope-SSE: enable`），可后置优化
- 优势：纯 HTTP + 标准库就能实现，和 `dashscope_tts.py` 风格一致，**不引入 dashscope SDK**

备选（不推荐先做）：Paraformer 实时 WS（延迟更低，但要自己实现 WS 协议）；本地 sherpa-onnx（断网可用，但 Pi 4 上吃 CPU，且模型 200MB+）。

### 3.2 LLM：DeepSeek + function calling

- 复用 `vision_llm.py` 的 `DEEPSEEK_API_KEY/BASE_URL/MODEL` 约定（模型 `deepseek-flash`＝V4.1-Flash）
- `stream=True`，逐句切分送 TTS，首句先出声
- `tools` 只挂 8 个（别把 21 个全给，LLM 会乱选）：

| 工具 | 用途 |
|---|---|
| `move_robot(direction, duration)` | 前后左右 |
| `rotate_robot(direction, angle)` | 转向 |
| `stop_robot()` | 急停（**任何异常都先调它**） |
| `look_and_analyze(question)` | 调车端 `capture_and_analyze`，走 DeepSeek 视觉 |
| `play_preset_action(action_id)` | 预设动作编排 |
| `get_robot_status()` | 电量/连接/位置 |
| `set_speed_level(level)` | 快慢档 |
| `control_gripper(action)` | 夹爪 |

### 3.3 TTS：DashScope `cosyvoice-v1`

- 直接调 `dashscope_tts.synthesize(text, voice=longxiaochun)` 拿 wav
- 解码成 16k 单声道 PCM（复用 `greeting/speech.py` 的 `decode_wav`）
- 分块（比如 200 ms）灌进 `hub.write_talk()`，边下边播，不等整句合成完

## 4. 协议设计（在现有 `:8081` 上扩展，不新增端口）

### 4.1 新增消息类型

| 方向 | 消息 | 说明 |
|---|---|---|
| 页面→车 | `{"type":"dialog","on":true}` | 开启对话会话（需持有控制权，走 `can_talk` 鉴权） |
| 页面→车 | `{"type":"dialog","on":false}` | 结束会话 |
| 页面→车 | `{"type":"dialog","action":"abort"}` | 打断（停止 TTS/LLM） |
| 页面→车 | 二进制帧 | **沿用现有格式**，会话开启时自动进 ASR 缓冲 |
| 车→页面 | `{"type":"dialog","event":"state","state":"listening\|thinking\|speaking\|idle"}` | 状态机 |
| 车→页面 | `{"type":"dialog","event":"asr","text":"...","final":true}` | 识别结果 |
| 车→页面 | `{"type":"dialog","event":"reply","text":"...","final":false}` | LLM 增量文字（做打字机） |
| 车→页面 | `{"type":"dialog","event":"tool","name":"move_robot","result":"..."}` | 执行了什么动作（给用户安全感） |
| 车→页面 | `{"type":"dialog","event":"error","message":"..."}` | 失败原因 |

**兼容性**：老前端不发 `dialog` 消息，行为完全不变；`hello` 里增加 `"dialog": true` 供前端探测能力。

### 4.2 关键改动点（`audio_ws.py:435`）

```python
# 现在
if client.ptt:
    self.hub.write_talk(client.id, bytes(message))

# 改成
if client.dialog and self.dialog:
    self.dialog.feed(client.id, bytes(message))   # 进 ASR 缓冲
elif client.ptt:
    self.hub.write_talk(client.id, bytes(message))
```

## 5. 状态机与仲裁（这是最容易出问题的部分）

```
IDLE ──按住说话──> LISTENING ──检测到静音 0.8s──> THINKING
                        │                          │
                        │(超时/太短)                ├─工具调用→(执行完继续)
                        └──> IDLE                  ↓
                                              SPEAKING ──播完──> IDLE
                                                   │
                                            用户打断/abort
                                                   ↓
                                                 IDLE
```

**四条铁律**

1. **半双工**：`SPEAKING` 期间丢弃上行帧。否则车喇叭的声音被麦克风收回去 → ASR 听到自己 → 自问自答死循环。页面上同步把「按住说话」置灰并提示"小智正在说话"。
2. **只有一个人能对话**：沿用现有 `can_talk` 鉴权（`audio_ws.py:526` 每次 PTT 前会重新鉴权），不额外造轮子。
3. **TTS 只在说话时占喇叭**：`begin_talk("ai-dialog")` → 写完 `end_talk()`。不要在会话期间一直持有，否则网页对讲会被永久锁死。
4. **异常先停车**：LLM/工具任何一步抛异常，先 `stop_robot()` 再回一句"我有点卡住了"。

**与现有功能的冲突处理**

| 场景 | 处理 |
|---|---|
| AI 说话时有人按网页对讲 | `begin_talk` 返回"已有用户在说话"，页面提示"小智在说话，稍等" |
| 网页对讲时开启对话 | 拒绝，提示先结束对讲 |
| 打招呼（有人靠近）与对话撞车 | 对话会话期间跳过打招呼（`greeting/policy.py` 加一个判断） |
| 对话中途有人进视野触发招呼 | 同上，跳过；对话结束后的下一次检测不受影响 |

## 6. 页面 UI

在现有「语音对讲」面板**下方**加一块，不挤占控制区：

```
┌─ 💬 AI 对话 ────────────────── [● 待命] ─┐
│                                          │
│   ┌──────────────────────────────┐       │
│   │ 你：往前走一点                │       │  ← 用户气泡（右）
│   └──────────────────────────────┘       │
│   ┌──────────────────────────────┐       │
│   │ 小智：好嘞，往前 30 厘米～     │       │  ← 回复气泡（左）
│   │ ▸ 已执行 move_robot          │       │  ← 动作痕迹（灰字）
│   └──────────────────────────────┘       │
│                                          │
│   [🎙 按住对话]  [⏹ 打断]  [轮次: 3]      │
│   ▁▂▄▆▃▁ (本地电平)                       │
│   ☑ 车端发声   ☐ 页面也播                 │
└──────────────────────────────────────────┘
```

- **按住对话**：沿用现有 `audio-ptt-btn` 的交互习惯（长按说话、松手结束），只是走 `dialog` 通道
- **状态徽章**：待命 / 聆听中 / 识别中 / 思考中 / 说话中，用现有 `setBadge()`（`audio_control.js:75`）
- **打断**：发 `{"action":"abort"}`，比"再说一句"更符合直觉
- **动作痕迹**：工具调用要在气泡里显形，否则用户不知道车为什么动了——安全上很重要
- 移动端（`mobile.html`）先不做，桌面端跑通再说

## 9. 延迟预算（要提前知道会给用户什么体感）

| 环节 | 预估 | 优化手段 |
|---|---|---|
| 端点检测（静音判定） | 0.8 s | 降到 0.5 s（易截断） |
| WAV 打包 + ASR 上传识别 | 0.6 ~ 1.2 s | ①SSE 流式 ②边录边传 |
| LLM 首 token | 0.8 ~ 1.5 s | 句子级切分，首句先 TTS |
| TTS 首包 | 0.5 ~ 0.9 s | 只合成第一句，播完再合下一句 |
| **合计到第一声** | **2.7 ~ 4.4 s** | 优化后可压到 ~2 s |

**这个延迟必须靠 UI 补**：`识别中/思考中` 状态 + 页面先显示文字，比干等体验好得多。

## 10. 分阶段落地

### 阶段 1：文字闭环（0.5 天）
先不管语音：页面上加个输入框 → DeepSeek → 回复文字 + TTS 车端播。
**验证**：TTS 能正确播到车上喇叭、不抢对讲、打招呼会让路。
> 这一步就能暴露 80% 的坑（声卡、wav 解码、hub 占用、超时）。

### 阶段 2：语音闭环无工具（1 天）
按住说话 → ASR → LLM（纯闲聊）→ TTS。加状态机 + 半双工。
**验证**：连续 5 轮对话不卡死、不自激、打断有效。

### 阶段 3：接工具（0.5 天）
挂 8 个工具，说"往前走一点"车真的动。动作必须回显。
**验证**：危险指令（"一直往前冲"）被 system prompt + duration 上限挡住。

### 阶段 4：体验优化（1~2 天）
ASR 流式、句子级 TTS、多轮上下文、氛围音、音量自适应。

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **自激回声**（喇叭→麦克风→ASR） | 死循环烧钱 | 半双工硬隔离；TTS 开始前丢弃缓冲；加"相似文本连续两次即中断"保护 |
| ASR 把口语识别歪 | 答非所问 | 页面显示识别文本并允许「重说」；`enable_itn` 开 |
| 网络抖动 | 卡在"思考中" | 每步 8 s 超时 + 明确报错语音；失败回文字 |
| DashScope 计费 | 成本不可控 | 会话级 `max_turns` 上限；空闲 60 s 自动结束会话；不录音落盘 |
| 车上喇叭音量过大 | 吓人/扰民 | 复用 `config.audio.talk_gain`，对话再乘一个 `dialog_gain`（默认 0.8） |
| LLM 幻觉乱指挥 | 车乱动 | 工具白名单 + `duration ≤ 3s` + 默认 `slow` 档 + 任何异常先 `stop_robot()` |

## 12. 待确认

1. **ASR 走云端还是本地？** 营地如果可能断网，就得考虑本地模型（Pi 4 上 ASR ~1 s，体验打折）。
2. **要不要多轮记忆？** 纯指令场景单轮就够；闲聊才需要上下文。
3. **页面也要出声吗？** 如果人在远处看画面，可能希望页面也能听到（`play_on_page`）。
4. **谁有权对话？** 现在 `can_talk`（持有控制权的人）才能对讲，对话要不要同样限制？
