# 自动打招呼方案（摄像头发现在人 → 说话 + 点头/摇头）

> 场景：小车停在营地帐篷里，面朝入口。有人进入视野时自动打招呼，并配一个头部动作。
> 本文是**设计推演与选型对比**。已经按此实现，操作手册见 [自动打招呼.md](自动打招呼.md)。

## 1. 目标与验收

| 项 | 目标 |
| --- | --- |
| 触发 | 有人进入画面并停留约 1 秒后才打招呼，**不是**一帧就喊 |
| 延迟 | 人站定到出声 ≤ 1.5 秒（预录音频）/ ≤ 2.5 秒（云端 TTS） |
| 动作 | 出声后 0.6 秒开始点头（或摇头），与语音并行，不互相阻塞 |
| 不扰民 | 同一个人 3 分钟内不重复打招呼；每小时最多 6 次；夜间闭嘴 |
| 可控 | 网页上一键开关；对讲中不插话；有人在操作机械臂时只出声不动手 |
| 可调试 | MCP 提供「立刻打一次招呼」工具，便于现场演示与排障 |

## 2. 现状盘查：能复用什么、缺什么

| 能力 | 现状 | 结论 |
| --- | --- | --- |
| 摄像头取帧 | `robot.cameras['front']`（T1 Webcam，640×480@30）、`async_read()` | ✅ 直接可用 |
| 点头/摇头动作 | `config/actions.json` 已有 `nod`（腕关节上下 3 次，6×0.3s+0.8s ≈ **2.6 秒**）、`shake_head`（腕关节左右 3 次） | ✅ 不用新写动作 |
| 动作执行器 | `core/actions.py` 的 `ActionPlayer`：线性插值、关节限位、临时提速、可急停、单实例 | ✅ 走它，别走 `nod_head()` |
| 喇叭播放 | `core/audio.py` 的 `IntercomHub.begin_talk(client_id)` → `write_talk(pcm)` → `end_talk()`，**独占** | ✅ 复用现有独占锁 |
| **人体检测** | **无**。全靠云端：`capture_and_analyze()` 单张分析（当时是 `qwen-vl-plus`，现已换 DeepSeek 多模态） | ❌ 需新增本地检测 |
| **语音播报** | **无 TTS**。只有对讲用的裸 PCM 通路 | ❌ 需新增（预录音频或云端 TTS） |
| 云端能力 | DeepSeek `DEEPSEEK_API_KEY`（视觉）+ DashScope `QWEN_API_KEY`（TTS）各自独立 | ✅ TTS 只能复用 DashScope，DeepSeek 无语音合成 |

**关键提醒**：`mcp/server.py` 里的 `nod_head()` / `shake_head()` 是**直接** `set_arm_position`（无插值、无锁、阻塞），不适合自动化调用。打招呼必须走 `ActionPlayer.play('nod')`，否则动作会顿挫且和网页/AI 的机械臂操作打架。

## 3. 整体架构

```
      3~4 fps 采样                        触发（边沿）
摄像头 ──► 检测器 ──► 状态机 ──┬──► 语音：ActionPlayer 无关，走 IntercomHub 独占喇叭
 (front)   (本地 ONNX)  (防抖/冷却) └──► 动作：ActionPlayer.play('nod' | 'shake_head')
                                        └──► 事件：网页状态栏 / 日志 /（可选）企业微信
```

一个后台线程 `GreeterWorker`，串起「取帧 → 检测 → 判定 → 演出」。放在 `moyurobot/core/greeter.py`，与 `streaming` / `audio_ws` 平级，由 `web/controller.py` 的 `run_server()` 启动。

### 状态机（核心，防"复读机"全靠这个）

```
IDLE ──连续 N 帧命中且占比达标──► CANDIDATE ──持续 ≥0.5s──► GREETING ──► COOLDOWN
  ▲                                    │                                   │
  └──────── 连续 M 秒无人（算离开）─────┴───────────────────────────────────┘
```

四条硬规则：

1. **必须是「由无到有」的边沿才触发**。人一直站在画面里，只在第一次触发，之后进入 `COOLDOWN`；期间再怎么检测到人都不会重复。
2. **离开判定**：连续 `leave_seconds`（默认 8s）无人，才回到可触发状态。避免人稍微转头/被遮挡就重置导致连环打招呼。
3. **冷却**：`cooldown_seconds`（默认 180s）内不再触发。
4. **速率上限**：`max_per_hour`（默认 6）兜底，防止营地人来人往时变成广播。

## 4. 检测方案选型

| 方案 | 精度 | Pi 上耗时 | 依赖 | 评价 |
| --- | --- | --- | --- | --- |
| **YOLO11n ONNX + onnxruntime**（首选） | 高，人无论正背都检出 | 320×320 约 60~100ms（Pi 5）/ 150~250ms（Pi 4） | `onnxruntime` + 6MB 模型 | 最快 |
| **YOLO11n ONNX + cv2.dnn**（实际最省事） | 同上 | 略慢于 onnxruntime | **只要 opencv + 模型** | 实施时新增：不用 pip 装任何东西就能跑 YOLO |
| `cv2.HOGDescriptor` 默认行人检测 | 差（必须全身、正背、光线好） | 320×240 约 100~150ms | 无（opencv 4.x 自带） | 兜底；**OpenCV 5.0 已移除该 API** |
| `cv2.FaceDetectorYN`（YuNet，337KB） | 只认脸，背对/低头就漏 | 约 10~20ms | 无（opencv 自带） | 可做 P2 的「是否正对我」增强，不适合单独当触发器 |
| `qwen-vl-plus` 云端 | 最高，还能顺带描述 | 1~3s + 每次约 ¥0.008 | 网络 | **不能做连续检测**。只适合触发后确认/生成问候语 |

**建议**：`detector: "auto"` —— 有模型且有 `onnxruntime` 就用它，只有模型就用 `cv2.dnn`，
都没有再退回 HOG（4.x）或直接报不可用（5.x）。降级要**只告警一次**，别在日志里刷。

### 距离门槛怎么定（单目没有深度，用 bbox 高度当代理）

640×480、水平 FOV 约 70° 时，人高 h 占画面高度的比例 ≈ **1.62 / 距离(m)**：

| `min_person_ratio` | 相当于人站在 | 适用 |
| --- | --- | --- |
| 0.16 | 10 m | 太远，帐篷外的路人也会触发 |
| **0.30（建议默认）** | 5.4 m 内 | 营地帐篷合适：入口及门口路过 |
| 0.45 | 3.6 m 内 | 更保守，人在门口才打招呼 |

另外加一条：**bbox 中心必须落在画面中央 70% 区域内**，避免边缘晃过的人触发。

## 5. 语音方案选型

| 方案 | 延迟 | 依赖 | 文案能否变 | 评价 |
| --- | --- | --- | --- | --- |
| **A. 预录音频池**（推荐起步） | < 50ms | 无 | 固定几句 | 断网/弱网也能用，营地信号差时唯一可靠 |
| B. 云端 TTS（DashScope CosyVoice / qwen-tts） | 0.8~1.5s | 网络 | 可动态（时间/天气/带娃） | 更像人；失败要能回退到 A |
| C. 本地 TTS（piper / espeak-ng） | 0.3~0.8s | 本地模型 | 可动态 | 音质一般、占 CPU；Pi 4 上不划算 |

**建议**：`speech.mode = "audio"` 起步（三到五句文案池随机），预留 `"tts"` 模式，`timeout_s: 1.5` 超时自动回退到预录音频。合成结果按文本哈希缓存到 `~/.cache/moyurobot/tts/`，同一句只调一次。

文案池示例（避免每辆车都一个腔调）：`你好呀～` / `欢迎来营地，随便看看～` / `嗨，需要帮忙吗？` / `我是小猫，今天在这儿值班～`

**播放要走对讲那条独占通道**：

```python
hub.begin_talk("__greeter__")   # 若有人正在 PTT，会直接返回「已有用户在说话」→ 天然仲裁
hub.write_talk("__greeter__", pcm_chunk)   # 按 chunk_ms 分块写，别一次性灌
hub.end_talk("__greeter__")     # 内部会 drain，播完才关
```

副作用要知道：`begin_talk` 会置 `_ptt_owner`，现有半双工逻辑会让**网页监听端在打招呼期间被静音**（防回授啸叫）。这是合理的默认行为，但如果你想在远程听到它打招呼，需要单独给监听端开一个「允许旁听 TTS」的例外。

## 6. 三个资源冲突与仲裁规则（最容易翻车的地方）

| 冲突 | 现状 | 规则 |
| --- | --- | --- |
| **喇叭** | `begin_talk` 独占，被占时返回失败 | 打招呼前先看 `hub.ptt_active`：正在对讲就**最多等 3 秒**，还占用就放弃这次语音（只做动作或直接跳过），绝不抢断人的说话 |
| **机械臂** | `ActionPlayer.play()` 会**先停掉**正在播的动作 | 触发时查 `action_player.get_state()['playing']`：正在播别人的动作 → 本次只出声不动手；`respect_arm_busy: false` 才允许抢占 |
| **摄像头帧** | `front` 目前被 `capture_and_analyze_with_qwen` 偶尔 `async_read`；lerobot 的 `async_read` 是队列消费，**多个读者会互相偷帧** | 检测器独占 `front`，并把最新帧缓存成一个 `latest_frame` 供其它模块读（顺带让拍照分析变快）。否则检测会把 AI 拍照的帧抢走，表现为"拍照偶发失败" |

## 7. 安全与分寸

- **时段**：`active_hours: "09:00-21:00"`，夜里不打招呼（营地夜里有人上厕所路过，吓人也吵人）。
- **一键静音**：网页状态栏加开关，落盘到配置，重启仍生效；优先级高于自动触发。
- **不落盘**：默认只在内存留最近一帧，`snapshot_dir` 为空即不存。营地是半公共场所，长期留存陌生人影像没必要也麻烦；要调试才显式打开。
- **音量**：单独 `speech.gain`，默认比对讲 `talk_gain` 低一档（打招呼不该像广播）。
- **动作幅度**：`nod` 只动腕关节，幅度小、安全；不建议用 `wave`（整臂抬起，帐篷内空间小，容易碰东西）。

  "detector": "auto",
  "model_path": "models/yolo11n.onnx",

  "respect_arm_busy": true,

## 9. 分阶段实施

| 阶段 | 内容 | 产出 |
| --- | --- | --- |
| **P0 先跑通（半天）** | HOG 或 YOLO + 预录 3 句 wav + `nod` + 冷却 + 边沿触发 + 开关 | 能在帐篷里演示"有人就打招呼"，先验证体感 |
| **P1 上生产（1~2 天）** | YOLO11n ONNX + 云端 TTS 兜底 + 时段/速率 + 网页状态与开关 + MCP 调试工具（`greeting_test` / `greeting_status`）+ 单元测试（状态机、冷却、资源仲裁全部可离线测） | 长期挂着不出事 |
| **P2 增强（可选）** | YuNet 判断"是否正对我" → 只对面向车的人打招呼；底盘微转向对准；熟人识别（本地人脸 embedding）用不同问候；把打招呼片段推企业微信 | 更像一个"人" |

## 10. 风险与必须先在 Pi 上实测的三个数字

1. **YOLO 单帧耗时**：`onnxruntime` 在你这块 Pi 上到底 60ms 还是 250ms，直接决定 `detect_fps` 能不能到 4。P0 前先跑个 30 行的 benchmark 脚本，别凭猜。
2. **帐篷内实际光照下的检出率**：帐篷内偏暗 + 门口逆光是最坏情况。建议预处理加 CLAHE；如果漏检严重，把 `input_size` 提到 416 或换 `yolo11s`（代价是帧率降一半）。
3. **喇叭与麦克风的物理距离**：打招呼时麦克风会收到自己的声音。现有半双工只防了"人说话"这条路径，TTS 播放这条新路径要实测会不会自激；必要时在播放期间暂停采集。

**可选硬件增强**：加一个 HC-SR501 人体红外（约 ¥10）做"有人靠近"的粗触发，摄像头只在被唤醒后的 10 秒内跑检测 —— CPU 占用和误报都能再降一个量级。纯软件方案也能用，这个是锦上添花。

## 11. 需要你确认的四个问题

1. **车头正对哪儿**？如果对着帐篷入口，`min_person_ratio` 按 0.30 起步；如果对着通道（人会从侧面路过），要收到 0.45 并加 `center_zone` 收紧。
2. **打招呼是"欢迎光临"还是"陪聊"**？前者固定文案即可；后者需要接 ASR + Qwen 对话，工作量翻倍。
3. **网络情况**？营地如果有稳定 Wi-Fi/4G，P1 就能上云端 TTS；否则死守预录音频。
4. **Pi 型号 + 有没有装 `onnxruntime`**？决定 P0 用 YOLO 还是先 HOG 顶上。
